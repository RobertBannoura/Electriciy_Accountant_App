# Production security checklist

Review date: 2026-09-10
Owner: deployment operator and application administrator

This checklist separates controls verified in the repository from controls that
must be completed in the real production environment. Do not use production or
client data to satisfy pre-production QA items.

## Release blockers

- [ ] Replace the five-character value in the ignored `server/.env`; rotate the
  admin password in every database where it may have been provisioned, then
  remove `ADMIN_PASSWORD` from the long-lived runtime environment.
- [ ] Complete HTTPS termination and HSTS verification at the Railway/reverse
  proxy. The loopback HTTP application intentionally does not emit HSTS.
- [ ] Complete the target-environment backup/restore drill and the physical
  inventory, opening-balance, and cash reconciliations below.

## Server

- [x] Production startup requires an explicit `NODE_ENV=production`.
- [ ] Supply the production `DATABASE_URL` through the server secret store.
- [ ] Use a least-privilege runtime database user limited to required
  read/write/sequence operations.
- [ ] Use a separate migration/deployment identity for schema-altering rights;
  remove those rights from the runtime identity.
- [ ] Terminate HTTPS at the trusted proxy and redirect HTTP to HTTPS.
- [ ] Emit a long-lived HSTS policy at HTTPS termination only after HTTPS is
  correct for the production host and all intended subdomains.
- [ ] Set `CLIENT_ORIGIN` to the one exact HTTPS production origin. Never use
  `*`, `null`, a path, or a credentialed URL.
- [x] Keep `ELECTRON_ORIGIN=app://renderer`; startup rejects alternatives.
- [ ] Confirm Railway/reverse-proxy forwarding and client-IP configuration.
  Do not enable broad `trust proxy` behavior without a new rate-limit review.
- [x] API errors suppress stack traces, SQL details, and exception messages.
- [x] Sensitive API responses and errors carry `Cache-Control: no-store`.
- [ ] Configure restricted log access, retention, alerting, clock
  synchronization, and incident-export procedures.

## Authentication

- [ ] Provision a unique password-manager-generated admin password of at least
  15 characters; no known/default/development password may be reused.
- [x] No default production password is shipped in tracked configuration.
- [x] Passwords use salted scrypt; opaque sessions are hashed in PostgreSQL and
  expire server-side after 12 hours.
- [x] Logout, account disablement/deletion, expiry, and password reprovisioning
  invalidate the applicable sessions.
- [ ] Document the controlled password-change procedure: run
  `npm run admin:provision` with a temporary secret, verify session revocation,
  then remove `ADMIN_PASSWORD` from runtime configuration.
- [x] Registration, forgot-password, reset-password, employee, cashier, and
  customer-account flows do not exist and were not introduced.

## PWA

- [ ] Serve the PWA and API only from their intended HTTPS origins.
- [x] Production build and local production preview serve the manifest and
  service worker successfully.
- [x] The service worker bypasses API, authenticated, cross-origin, and all
  non-GET requests.
- [x] There is no financial offline queue, Background Sync handler, IndexedDB
  replay database, or automatic write replay.
- [ ] Verify service-worker installation, update, cache eviction, logout, and
  offline UI behavior on the real production origin.

## VAPID and Web Push

- [ ] Generate a new production VAPID pair using the hardened generator.
- [ ] Store the private key only in the backend secret store; expose only the
  public key to clients.
- [ ] Rotate any pair generated by the former stdout-printing implementation if
  terminal or CI logs may have retained it.
- [ ] Test subscription, delivery, permission denial, expiration, `404`/`410`,
  and temporary failure behavior in current Chrome and Edge on real devices.
- [x] Disposable HTTPS integration proved authenticated/encrypted Web Push,
  owner-scoped subscriptions, post-commit dispatch, and safe failure isolation.

## Electron

- [x] Windows x64 production package rebuilt with supported Electron 44.3.0.
- [x] Packaged DevTools are disabled and packaged `--dev` cannot load a
  development renderer.
- [x] Context isolation, renderer sandboxing, disabled Node integration,
  origin-checked narrow IPC, denied permissions, denied webviews, and blocked
  navigation are verified.
- [x] Both the source-runtime smoke and freshly packaged executable smoke loaded
  the secure admin login screen on Windows.
- [ ] Code-sign the executable/installer with the organization's trusted
  certificate before distribution.
- [ ] Install on the target Windows account and verify ACLs on the installation,
  Electron user-data, device-settings, and backup directories.
- [ ] Confirm the operator-selected backup directory is access-controlled and
  resides on encrypted storage.

## Hardware

- [ ] Test the physical barcode scanner against representative product codes.
- [ ] Generate a barcode, print it, and rescan the printed result.
- [ ] Test the supported barcode printer, paper size, density, and RTL labels.

## Backup and restore

- [ ] Select the production backup folder and verify its ACLs, encryption,
  available space, retention, and off-device copy policy.
- [ ] Create and independently verify a manual backup.
- [ ] Enable automatic backup and prove the daily guard and operator warning in
  the installed application.
- [ ] Restore a production-shaped but non-client test backup into an isolated
  restore environment; reconcile it and document recovery time.
- [x] Disposable PostgreSQL tests proved checksums/schema validation,
  allowlisted data, transactional restore, corrupted-restore rollback, and
  authentication/session exclusion.

## Financial production acceptance

- [ ] Run **فحص الحسابات** against the production candidate and require a clean
  result before opening operations.
- [ ] Verify opening inventory per product and store against a signed physical
  count.
- [ ] Verify customer and supplier opening balances against approved source
  statements.
- [ ] Verify physical ILS, USD, and JOD cash separately and reconcile bank
  opening balances.
- [x] Disposable adversarial PostgreSQL tests proved authoritative totals,
  immutable FX/COGS snapshots, replay protection, concurrency locks, rollback,
  check state transitions, returns, and corruption detection.
